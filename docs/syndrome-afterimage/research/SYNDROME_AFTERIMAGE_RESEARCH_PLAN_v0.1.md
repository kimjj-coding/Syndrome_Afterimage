# 신드롬: 잔상 (SYNDROME: AFTERIMAGE)
## 연구 설계 계획서 v0.1

- 문서 상태: 초안 — 조사 결과에 따라 수정 예정
- 현재 단계: 연구 설계
- 제품 형태: 웹 브라우저에서 실행되는 게임
- 기본 원칙: 근거 없는 낙관을 피하고, 중요한 가정은 작은 검증으로 확인한 뒤 다음 단계로 진행한다.

---

## 1. 연구 목적

이 연구의 목적은 기존 아이디어를 그대로 구현하는 것이 아니다. 심리 호러라는 핵심 정체성을 살리면서도, 플레이어가 실제로 탐험·관찰·추리·선택·회피를 하며 재미를 느끼고, 초보 개발자가 웹 환경에서 단계적으로 제작할 수 있는 게임 구조를 찾는 것이다.

최종적으로 아래 질문에 답해야 한다.

1. 이 게임의 핵심 플레이 경험은 무엇인가?
2. 그 경험을 만들어내는 데 반드시 필요한 시스템과 없어도 되는 시스템은 무엇인가?
3. 심리적 경험과 정신건강 주제를 부정확하거나 낙인찍는 방식 없이 어떻게 표현할 것인가?
4. 2D, 2.5D, 3D 중 어떤 관점과 조작 체계가 목표 경험·예산·제작 난도에 가장 잘 맞는가?
5. 브라우저에서 어떤 기술 스택으로 구현하면 초보 개발자가 유지·테스트하기 쉬운가?
6. 숨겨진 선택 변수와 여러 엔딩은 어떻게 구성해야 결과가 임의적이지 않으면서도 쉽게 공략되지 않는가?
7. 어떤 최소 프로토타입을 만들면 핵심 가정을 가장 싸고 빠르게 검증할 수 있는가?

## 2. 확정된 사항과 미확정 사항

### 현재 확정된 방향

- 목표 플랫폼은 별도 콘솔 게임이나 네이티브 앱이 아닌 **웹 브라우저**다.
- 심리 호러, 탐험, 단서 및 기억 조각, 선택에 따른 결과, 추격·회피 구간, 여러 엔딩을 후보 핵심 요소로 삼는다.
- 기존 아이디어는 연구와 테스트에 따라 수정·삭제할 수 있다.
- 무료 또는 저비용 도구를 우선하며, 큰 작업에 앞서 가능성을 검증한다.
- 실제 게임 사례를 연구하되, 기존 게임의 요소를 그대로 복제하지 않고 원리와 적용 가능성을 분석한다.

### 아직 확정하지 않을 사항

- 2D / 2.5D / 3D 및 카메라 시점
- 키보드·마우스, 터치, 게임패드 지원 범위
- Phaser + TypeScript, 다른 게임 엔진 또는 프레임워크 중 최종 기술 스택
- 주인공·세계관·스테이지의 최종 구성
- 숨겨진 수치의 개수와 명칭, 계산 방식
- 초기 구상에 있던 여섯 엔딩의 유지 여부와 조건
- 저장 방식, 백엔드·계정 기능 필요 여부
- 최종 플레이 시간과 전체 콘텐츠 규모

현재의 MBV, RI 등의 수치 체계는 검증 전 임시안으로 본다. 수치를 남기는 것보다 플레이어 행동과 게임 결과 사이의 일관된 관계를 만드는 것이 우선이다.

## 3. 연구 원칙

1. **증거와 추측을 분리한다.** 문서의 핵심 주장을 `확인된 사실`, `근거가 있는 해석`, `검증할 가설`, `미결정`으로 표시한다.
2. **기능보다 플레이 경험을 우선한다.** 기능이 멋있어 보인다는 이유만으로 추가하지 않는다.
3. **게임 사례는 원리 중심으로 비교한다.** 어떤 요소가 어떤 경험을 만들며, 다른 규모와 플랫폼에서도 재현 가능한지 분석한다.
4. **구현 난도를 과소평가하지 않는다.** 3D, 복잡한 애니메이션, 음성 연기, 수많은 분기, 실시간 추격을 모두 한 번에 만들 수 있다고 가정하지 않는다.
5. **심리·정신건강 묘사는 별도 검증한다.** 외상 반응, 침투적 기억, 회피, 해리 경험, 공황, 정신증적 경험, 조현병 등을 같은 개념으로 취급하지 않는다. 폭력성과 정신질환을 자동으로 연결하지 않는다.
6. **선택에는 사후적으로 추적 가능한 근거가 있어야 한다.** 결과를 미리 쉽게 알 수 없더라도, 플레이 후에는 어떤 행동과 단서가 결과에 영향을 주었는지 이해할 수 있어야 한다.
7. **접근성과 안전 옵션을 설계에 포함한다.** 강한 깜박임, 화면 왜곡, 급격한 음량 변화, 불쾌한 음향은 조절하거나 줄일 수 있는 대안을 검토한다.
8. **연구를 구현으로 연결한다.** 연구 결과마다 실제 설계 결정, 테스트 방법 또는 보류 사유가 있어야 한다.

## 4. 연구 질문과 작업 흐름

### 작업 0 — 프로젝트 범위와 성공 기준

핵심 질문:
- 플레이어가 반복해서 수행하게 될 핵심 행동은 무엇인가?
- 플레이어가 느껴야 하는 감정과 내려야 하는 판단은 무엇인가?
- 게임의 차별점은 선택지의 개수, 세계 탐험, 심리적 해석, 추격 등 중 무엇인가?
- 첫 번째 검증 가능한 버전에 어디까지 넣을 것인가?

산출물:
- 한 페이지 프로젝트 개요
- 플레이어 경험 목표 3~5개
- 범위 밖 항목 목록
- 핵심 가정 및 위험 목록

### 작업 1 — 게임 사례 연구

후보 작품은 최종 선정 전 조사 편의상 잡아 둔 목록이며, 모두 동일한 깊이로 조사할 필요는 없다.

| 후보 작품 | 조사할 관점 | 적용 시 주의점 |
|---|---|---|
| INSIDE | 환경을 통한 서사 전달, 이동·퍼즐·추격의 연결 | 완성도 높은 연출을 소규모 제작에 그대로 요구하지 않는다. |
| LIMBO | 제한된 조작, 실루엣과 환경 퍼즐, 실패 피드백 | 단순한 조작이 곧 단순한 제작을 뜻하지는 않는다. |
| Little Nightmares | 2.5D 공간, 크기 대비, 추격과 은신의 긴장 | 애니메이션·아트 제작량을 따로 평가한다. |
| Detention | 2D 심리 호러, 장소·역사·문화적 맥락 | 특정 사회·문화의 맥락을 피상적으로 차용하지 않는다. |
| Oxenfree | 대화 흐름, 인물 관계, 음향과 초자연 현상의 연결 | 시간제 대화가 접근성·이해도에 미치는 영향도 본다. |
| Slay the Princess | 반복 플레이, 상태 누적, 선택과 인물 변화 | 대규모 분기 콘텐츠 비용과 웹 게임 규모를 비교한다. |
| What Remains of Edith Finch | 공간·사물 중심 스토리텔링, 짧은 상호작용의 다양성 | 각 상호작용이 서사 외에 어떤 역할을 하는지 살핀다. |
| Fran Bow 또는 유사한 포인트앤클릭 게임 | 오브젝트 조사, 인벤토리 조합, 퍼즐 피드백 | 정신건강 표현은 별도의 정확성 기준으로 검토한다. |
| Yume Nikki 또는 유사한 비선형 탐험 게임 | 목적이 불분명한 탐색, 기이한 공간, 발견의 보상 | 불친절함과 의도적인 모호함을 구분한다. |

각 작품은 다음 기준으로 분석한다.
- 플레이어의 기본 반복 행동(loop)
- 이동·조사·퍼즐·추격·대화가 연결되는 방식
- 플레이어가 다음 행동을 추론할 수 있게 해주는 단서
- 실패, 재시도, 체크포인트의 처리
- 시각·소리·텍스트가 공포를 만드는 역할
- 콘텐츠와 애니메이션 제작량에 대한 대략적 부담
- 웹 브라우저 게임에 옮길 수 있는 원리와 옮기기 어려운 요소

산출물:
- 사례별 분석 카드
- 공통 원리와 서로 충돌하는 설계 선택
- 가져올 원리 / 수정해서 적용할 원리 / 적용하지 않을 원리 목록

### 작업 2 — 심리·정신건강 주제와 책임 있는 표현

핵심 질문:
- 게임에서 다룰 경험을 특정 진단명 없이 어떤 방식으로 묘사할 수 있는가?
- 외상 기억, 회피, 과각성, 공황, 해리, 죄책감, 애도, 사회적 압박 등을 서로 구별해 표현하려면 무엇을 주의해야 하는가?
- 비현실적인 공간과 감각 왜곡을 인물의 실제 정신질환 진단처럼 단정하지 않고 서사적 장치로 쓸 수 있는가?
- 플레이어의 선택이나 엔딩을 질병의 심각도 또는 도덕성 점수처럼 보이지 않게 하려면 어떤 설계가 필요한가?
- 내용 안내, 화면 효과 감소, 음량 조절, 자막 및 시각·청각 대체 정보가 필요한가?

자료 기준:
- 정부·공공 보건기관과 전문 의료기관의 안내
- 동료심사를 거친 연구 및 체계적 문헌 검토
- 당사자 경험을 다룬 자료는 보완 자료로 사용하고, 단일 경험을 모든 사람에게 일반화하지 않는다.
- 게임 제작자 인터뷰와 대중 리뷰는 연출·수용 분석에는 활용하되, 의학적 사실을 입증하는 근거로 사용하지 않는다.

산출물:
- 심리 개념별 표현 가이드
- 잘못된 등치·낙인 위험 목록
- 장면별 콘텐츠 경고 및 접근성 요구사항
- 게임 속 가상 지표와 현실의 임상 평가를 구분하는 규칙

### 작업 3 — 핵심 게임플레이 시스템

검토 대상:
- 탐험 및 환경 상호작용
- 단서·기억 조각 수집과 해석
- 인벤토리 및 오브젝트 조합
- 환경 퍼즐과 잠긴 경로
- 은신·회피·추격
- 대화 및 관계 변화
- 소리 단서와 시야·조명 변화
- 지도·되돌아가기·장소 변화
- 안전 구역, 체크포인트, 저장 및 재시도
- 반복 플레이 시 달라지는 정보와 이벤트
- 플레이어의 행동 기록과 증거 추적

각 후보는 다음 항목을 0~5점으로 평가한다.
- 핵심 주제에 대한 기여
- 플레이어가 실제로 판단하거나 숙달할 여지
- 다른 시스템과의 결합 가치
- 재플레이 가치
- 초보 개발자가 구현·테스트할 현실성
- 접근성과 조작 편의성

평가 점수는 객관적인 과학적 측정치가 아니라 결정을 비교 가능하게 만들기 위한 도구다. 점수가 높아도 제작 범위나 핵심 경험과 충돌하면 채택하지 않는다.

산출물:
- 필수 / 선택 / 보류 / 제외 시스템 표
- 시스템별 입력, 상태, 피드백, 실패·복구 규칙
- 핵심 반복 플레이 구조 초안

### 작업 4 — 선택·숨겨진 상태·엔딩 구조

핵심 질문:
- 플레이어의 선택 외에 탐험, 단서 해석, 회피·도움 요청 같은 행동을 어떻게 기록할 것인가?
- 단일 점수로 모든 행동을 판단하는 방식보다 여러 행동 태그와 증거 플래그를 분리하는 편이 나은가?
- 비슷해 보이는 선택이 상황에 따라 다른 의미를 갖게 하려면 맥락과 사후 피드백을 어떻게 설계할 것인가?
- 엔딩 조건이 서로 겹칠 때 우선순위를 어떻게 정할 것인가?
- 플레이어가 결과를 미리 완벽히 계산하기 어렵더라도 결과를 임의의 벌칙처럼 느끼지 않게 하려면 무엇이 필요한가?

잠정 검토안:
- 긴장도 같은 연속 수치
- 회피·직면·도움 요청·통제·보복 등 행동 태그
- 수집한 증거·기억 조각 플래그
- 특정 인물과의 관계 및 주요 사건 기록

이들은 후보일 뿐이며, 가장 단순하게 핵심 경험을 만드는 구조를 우선한다.

산출물:
- 상태 변수 명세
- 선택 결과 테이블
- 엔딩 조건과 우선순위 규칙
- 조건 충돌 및 경계값 테스트

### 작업 5 — 카메라, 조작, 웹 기술 및 성능

핵심 질문:
- 2D 횡스크롤, 탑다운, 고정 화면, 2.5D, 3D 중 어떤 형태가 핵심 경험을 가장 잘 전달하는가?
- 선택한 시점에서 이동, 상호작용, 퍼즐, 추격을 일관되게 만들 수 있는가?
- 키보드·마우스와 터치 중 무엇을 필수 지원해야 하는가? 화면 크기와 입력 차이가 플레이를 해치지는 않는가?
- 브라우저에서 필요한 저장, 오디오, 화면 전환, 리소스 로딩, 일시정지, 재시도는 어떻게 구현할 것인가?
- 게임 엔진과 프레임워크 후보의 문서 품질, 개발 난도, 빌드 결과, 접근성, 무료 배포 가능성을 어떻게 비교할 것인가?

기술 후보에는 Phaser + TypeScript를 포함하되, 지금 확정하지 않는다. 필요하면 더 단순한 HTML/CSS/JavaScript 방식이나 다른 2D 엔진과 비교한다. 서버·계정·클라우드 저장은 제품 경험에 꼭 필요하다는 증거가 없으면 초기 범위에서 제외한다.

산출물:
- 카메라·입력 방식 비교표
- 기술 스택 비교표와 권고안
- 자산·씬·상태 관리 구조
- 브라우저 및 기기 테스트 계획

### 작업 6 — 그래픽, UI, 사운드, 접근성

핵심 질문:
- 제한된 제작 리소스로 일관된 공포 미술 스타일을 유지하려면 어떤 표현 방식이 적합한가?
- 캐릭터·적·환경에 필요한 애니메이션과 상호작용 피드백은 무엇인가?
- 제목 화면, 일시정지, 대화, 선택지, 조사 화면, 인벤토리, 설정, 체크포인트, 엔딩 화면의 최소 요구사항은 무엇인가?
- 화면 왜곡·깜박임·소음·음량 급변을 줄일 수 있으면서 분위기를 유지할 대안은 무엇인가?
- 이미지·음향·폰트의 라이선스와 출처를 어떻게 기록할 것인가?

산출물:
- 아트 스타일 가이드 및 자산 목록
- UI 화면 목록과 상태별 전환 명세
- 사운드 사용 규칙
- 접근성 옵션 및 반응형 화면 요구사항
- 에셋 라이선스 기록 형식

### 작업 7 — 구현 워크플로 및 품질 검증

핵심 질문:
- 초보 개발자가 AI 코딩 도구를 사용할 때 작업 크기, 파일 범위, 테스트를 어떻게 제한할 것인가?
- 각 기능이 완료되었다고 판단할 수 있는 재현 가능한 테스트는 무엇인가?
- 브라우저 오류, 저장 실패, 터치 입력, 키보드 포커스, 오디오 시작 제한, 화면 비율 문제를 어떻게 확인할 것인가?
- 무료 호스팅과 빌드·배포 절차는 얼마나 단순하게 유지할 수 있는가?

산출물:
- 저장소 구조 및 문서 목록
- `.github/copilot-instructions.md` 초안
- 기능별 구현 순서와 완료 조건
- 회귀 테스트 및 버그 기록 방식

## 5. 자료 수집·검증 기준

### 자료 신뢰도

- **A — 1차·권위 자료:** 공식 기술 문서, 공공 보건기관, 연구 논문 원문, 개발자가 직접 설명한 자료
- **B — 보완 자료:** 신뢰할 수 있는 전문 매체, 인터뷰, 심층 분석, 전문 리뷰
- **C — 탐색용 자료:** 포럼·커뮤니티 의견, 짧은 리뷰, 개인 경험담

C 자료는 질문이나 사용자 반응을 찾는 데 쓸 수 있지만, 핵심 사실을 단독으로 확정하는 데 사용하지 않는다. 중요한 주장에는 가능하면 복수의 독립된 근거를 대조하고, 자료가 불일치하면 불일치 사실을 기록한다.

### 조사 기록 형식

각 조사 항목에는 다음을 기록한다.
- 질문
- 자료명, 작성자/기관, 날짜, URL
- 출처 유형과 신뢰도
- 확인한 주장 및 근거
- 다른 자료와의 일치·불일치
- 게임 설계에 미치는 영향
- 확신 수준과 추가로 필요한 검증

## 6. 설계 선택 평가 방식

후보 설계는 단순히 가장 멋있어 보이는 것을 고르지 않는다. 아래 기준을 이용해 비교한다.

| 기준 | 확인할 질문 |
|---|---|
| 주제 적합성 | 심리 호러와 핵심 경험에 직접 기여하는가? |
| 플레이 가치 | 플레이어가 관찰·판단·숙달하거나 발견할 수 있는가? |
| 시스템 시너지 | 다른 시스템과 유의미하게 연결되는가? |
| 제작 실현성 | 초보 개발자와 제한된 자원으로 만들고 고칠 수 있는가? |
| 명확성·공정성 | 규칙을 완벽히 미리 알 수 없어도 결과가 임의적으로 느껴지지 않는가? |
| 접근성 | 조작·시각·청각 효과 때문에 불필요하게 배제되는 플레이어가 생기지 않는가? |
| 유지 비용 | 추가 콘텐츠, 테스트, 자산 제작 부담이 감당 가능한가? |

하드 게이트도 함께 적용한다. 핵심 시스템을 구현할 방법이 불명확하거나, 저작권·안전·접근성 문제를 해결할 수 없거나, MVP 안에서 검증할 수 없다면 채택을 보류한다.

## 7. 검증 단계와 통과 조건

### Gate 0 — 조사 준비 완료

통과 조건:
- 핵심 질문과 조사 영역이 정의되어 있다.
- 조사 결과를 기록할 형식과 출처 기준이 있다.
- 미확정 사항을 성급하게 확정하지 않았다.

### Gate 1 — 콘셉트·핵심 루프 검증

통과 조건:
- 플레이어의 기본 반복 행동을 한 문단과 간단한 흐름도로 설명할 수 있다.
- 핵심 메커니즘과 보조 메커니즘을 구분했다.
- 후보 시스템을 모두 넣지 않아도 게임 정체성이 유지되는 이유를 설명할 수 있다.

### Gate 2 — 기술 및 제작 실현성 검증

통과 조건:
- 선택한 기술로 장면 전환, 이동, 상호작용, 상태 변경, 저장·재시작 등 필요한 핵심 기능을 구현할 수 있다는 근거가 있다.
- 기기와 브라우저를 정하고 기본 입력이 동작하는 실험 결과가 있다.
- 무료/저비용으로 시험 가능한 작업 경로가 정해져 있다.

### Gate 3 — 수직 슬라이스(MVP) 검증

예상 범위:
- 작은 탐험 공간 하나
- 조사 가능한 단서·기억 오브젝트 약 3개
- 맥락이 다른 선택 세트 하나
- 짧은 추격 또는 회피 시퀀스 하나
- 최소한의 행동/증거 상태 기록
- 상태에 따라 달라지는 결말 또는 명확한 결과 하나

통과 조건:
- 플레이어가 안내를 통해 이동·조사·선택을 수행할 수 있다.
- 단서와 선택이 서로 무관한 장식이 아니라 이후 결과에 영향을 준다.
- 추격·실패·재시도가 막히지 않고 반복 테스트 가능하다.
- 선택 결과가 완전히 예측 가능하지 않아도, 플레이 후 근거를 되짚을 수 있다.
- 목표 브라우저에서 치명적인 오류 없이 플레이 세션을 끝낼 수 있다.
- 효과를 줄이는 설정과 기본적인 UI 피드백을 시험할 수 있다.

성능 수치와 지원 브라우저는 기기·도구 조사를 거쳐 정한다. 지금 임의의 FPS나 로딩 기준을 확정하지 않는다.

### Gate 4 — 전체 기획서 작성 승인

통과 조건:
- 핵심 루프와 카메라·입력·기술 스택이 검증되었다.
- 심리 묘사 가이드와 선택·엔딩 로직이 모순 없이 정리되었다.
- 자산 제작량과 콘텐츠 범위에 현실적인 한도가 설정되었다.
- 기능별 테스트 기준을 쓸 수 있을 만큼 규칙이 구체적이다.

Gate를 통과하지 못하면 무조건 계속하지 않는다. 문제를 축소·수정하거나, 기술 대안을 실험하거나, 해당 기능을 제외한다.

## 9. 전체 진행 계획 — 재정리본

이 절은 프로젝트의 상위 진행 순서를 정의한다. 기존의 세부 연구 질문, 자료 신뢰도 기준, 설계 평가 기준, Gate 통과 조건과 산출물 구조는 아래 단계의 세부 실행 기준으로 유지한다. 상위 계획과 세부 항목이 겹치거나 충돌하면, 최신 검토 결과를 기록하고 확정 상태를 명시한다.

### 0단계 — 기존 기획과 조사 결과 감사

**지금 수행할 작업**

기존 아이디어, 연구 계획서, 앞서 작성된 조사 보고서를 한데 모아 정리한다. 이미 조사한 것과 실제 검증이 끝난 것을 구분하고, 출처가 약하거나 서로 충돌하는 결론은 다시 확인한다.

**결과물**
- 조사 항목 전체 목록
- 항목별 진행 상태표
- 미해결 질문 목록
- 수정 또는 재검증이 필요한 기존 결론

### 1단계 — 게임 사례와 핵심 플레이 경험 조사

기존 보고서의 검증 및 보완이 필요하다.

INSIDE, LIMBO, Little Nightmares, Detention, Oxenfree 등의 후보 작품을 비교한다. 단순히 유명한 작품을 나열하지 않고, 탐험·퍼즐·추격·은신·환경 서사·대화·선택이 실제로 어떻게 작동하는지와 소규모 브라우저 게임에 옮길 수 있는지를 조사한다.

**결과물**
- 사례별 분석표
- 재사용할 설계 원리와 제외할 원리
- 후보 핵심 플레이 루프

### 2단계 — 심리학·정신의학 표현 조사

**상태: 심층 리서치 진행 요청 완료 · 결과 검토 필요**

외상 반응, 해리, 정신병적 경험, 조현병 등을 구분하고 실제 근거와 창작적 해석을 분리한다. 정신건강 낙인, 진단의 오용, 시청각 연출의 위험도 확인한다.

**결과물**
- 근거 수준이 표시된 표현 가이드
- 피해야 할 묘사 목록
- 장면 검수 기준

이 조사가 끝나더라도 다음 단계로 바로 제작에 들어가지 않는다. 다른 연구 영역과 종합 검토를 거친다.

### 3단계 — 게임플레이 시스템 조사

탐험, 상호작용, 기억 조각, 단서 추론, 퍼즐, 인벤토리, 은신, 추격, 실패와 재시도, 체크포인트, 반복 플레이를 각각 검토한다.

핵심 질문은 무엇이 실제 재미를 만드는지, 어떤 기능이 다른 기능과 겹치는지, 어떤 기능이 제작비만 높이고 핵심 경험에는 거의 기여하지 않는지다.

**결과물**
- 시스템별 필요성·구현 부담·테스트 가능성 비교표

### 4단계 — 선택·상태 변수·분기·엔딩 조사

숨겨진 수치 하나로 모든 행동을 평가하는 방식, 행동 유형별 기록, 증거 플래그, 인물 관계, 사건 기록 등을 비교한다. 선택의 결과가 임의적인 벌칙처럼 느껴지지 않는지도 살핀다.

**결과물**
- 상태 관리 방식 비교
- 분기 비용 분석
- 엔딩 구조 후보
- 조건 충돌 및 경계값 테스트 기준

기존 MBV·RI 수치와 여섯 엔딩은 검증 전까지 확정하지 않는다.

### 5단계 — 브라우저 기술·시점·조작·저장 조사

2D·2.5D·3D와 카메라 후보, 키보드·마우스·터치 입력, 엔진·프레임워크, 브라우저 호환성, 로컬 저장, 배포 방법을 비교한다.

Phaser + TypeScript는 후보일 뿐이다. 공식 문서, 유지보수성, 초보자 학습 부담, 기기 성능, 실제 실험 결과를 바탕으로 판단한다.

**결과물**
- 기술 후보 비교표
- 기기·브라우저 요구사항
- 저비용 검증 방법

### 6단계 — 그래픽·애셋·UI·오디오·접근성 조사

픽셀 아트와 다른 스타일의 제작 부담, 무료 에셋의 라이선스, 애니메이션 제작량, 왜곡 효과, 사운드 구현, 자막, 효과 감소 설정, 반응형 화면과 키보드 접근성을 비교한다.

**결과물**
- 현실적인 아트 방향 후보
- 에셋 비용 및 라이선스 기록표
- UI 목록
- 사운드·접근성 요구사항

### 7단계 — 종합 검토와 가설 검증

앞선 조사 결과를 한자리에 모은다. 심리적 주제에는 적합하지만 구현하기 어려운 기능, 기술적으로는 가능하지만 재미가 불분명한 기능처럼 서로 충돌하는 결론을 비교한다.

**결과물**
- 우선순위가 정해진 기능 후보
- 제외·보류 목록
- 아직 검증되지 않은 가정
- 추가 실험이 필요한 항목

### 8단계 — 통합 기획서와 GitHub Copilot 작업 명세 작성

앞선 조사와 실험을 통과한 내용만 실제 설계 문서로 전환한다. 기능별 입력, 상태, 출력, 예외 처리, 완료 조건, 테스트 방법을 명시한다.

**결과물**
- 제품 범위
- 게임 기획 및 시스템 명세
- 스토리·분기·엔딩 명세
- 기술 명세
- 접근성 규칙
- 테스트 명세
- GitHub Copilot 지침

### 9단계 — 작은 프로토타입과 플레이 테스트

이 단계부터 실제 제작을 시작한다. 처음부터 전체 게임을 만들지 않고 핵심 경험을 검증하는 데 필요한 최소 기능만 구현한다. 테스트 결과가 나쁘면 기능을 줄이거나 설계를 바꾼다.

**결과물**
- 재현 가능한 테스트 결과
- 버그 목록
- 테스트 결과를 반영한 수정 기획서
- 다음 구현 단계의 진행 여부에 대한 근거 기반 판단

## 10. 현재 상태 요약

- **연구 계획서:** 초안 작성 완료. 이 절의 전체 진행 계획을 상위 실행 순서로 사용한다.
- **기존 조사 자료:** 초기 요약과 일부 심층 리서치 결과가 존재하지만, 이를 모두 독립 검증이 끝난 결론으로 간주하지 않는다.
- **심리·정신건강 조사:** 심층 리서치 요청 완료, 결과 검토 및 근거 확인 필요.
- **사례 연구·시스템 비교·기술 검증:** 개별 자료와 실험 결과를 추가 확인해야 한다.
- **미확정 결정:** 시점, 조작, 엔진·프레임워크, 상태 변수, 엔딩 구조, 콘텐츠 규모.
- **제작 시작 기준:** 앞선 조사와 종합 검토를 통과한 뒤, 핵심 경험을 검증할 최소 프로토타입부터 시작한다.
